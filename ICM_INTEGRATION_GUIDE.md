# Руководство по интеграции ICM Music Partner API: Перенос Плейлистов, Профиль и Подписка

Настоящий документ содержит исчерпывающее техническое руководство и спецификацию интеграции **ICM Music Partner API** в проект **LiquidMusicGlass**. Руководство охватывает архитектурные решения, схемы авторизации, маппинг моделей, алгоритмы импорта и поллинга, а также разбор критических исправлений для обеспечения полной стабильности приложения.

---

## 1. Схема Авторизации и Сессии (Auth System)

Интеграция с ICM API опирается на двухкомпонентную модель авторизации:
1. **Ключ партнера (`X-Partner-Key`)**: Формат `pk_<id>_<random>`. Хранится на бэкенде или в защищенной конфигурации клиента (`BuildConfig.ICM_API_KEY`).
2. **Сессионный токен JWT (`Authorization: Bearer`)**: Выпускается для конкретного пользователя (`partner_user_id`) на ограниченное время (по умолчанию 1 час). Необходим для всех эндпоинтов медиатеки и личного кабинета (`/me/*`).

### Выпуск сессии (`/session/issue`):
Перед отправкой запросов к `/me/*` приложение проверяет наличие локального кэшированного JWT. Если токен отсутствует или истек, бэкенд (или клиент с помощью ключа) отправляет запрос:
```http
POST /api/partner/session/issue
X-Partner-Key: pk_...
Content-Type: application/json

{
  "partner_user_id": "tg_12345",
  "hide_explicit": false
}
```
**Ответ сервера (200 OK)**:
```json
{
  "partner_session_token": "eyJhbGci...",
  "expires_in": 3600,
  "partner_user_id": "tg_12345",
  "scopes": ["search", "stream", "playlists_import"]
}
```
Токен сохраняется в памяти `IcmApi` и автоматически добавляется в заголовки:
`Authorization: Bearer <token>`

## 2. Интеграция Профиля и Управления Подпиской

Экран профиля (`ProfileScreen.kt`) осуществляет динамическое взаимодействие с аккаунтом ICM.

### 2.1 Линковка (Связывание аккаунтов)
Пользователь может привязать свое приложение к ICM двумя способами:
1. **Способ 1: Через Telegram (HTML-редирект)**
   Генерируется специальная ссылка авторизации через Telegram-бота партнера. Пользователь авторизуется в браузере, и бот осуществляет редирект с возвратом JWT.
2. **Способ 2: Через Email (JSON API с авторегистрацией)**
   Пользователь вводит email и пароль. Если аккаунта нет, система автоматически регистрирует его и связывает с `partner_user_id` приложения.

### 2.2 Информация о подписке и профиле
После авторизации приложение запрашивает данные о пользователе и статусе его подписки.

**Запрос профиля (`GET /me/profile`)**:
```json
{
  "icm_user_id": 42,
  "partner_user_id": "tg_12345",
  "email": "user@example.com",
  "chosen_region": "us",
  "created_at": 1747200000
}
```

**Запрос подписки (`GET /me/subscription`)**:
```json
{
  "status": "active",
  "expires_at": 1780000000,
  "type": "premium",
  "features": ["high_quality", "offline_sync"]
}
```

### 2.3 Выбор качества стрима (`streamQuality`)
Пользователь может настроить качество аудиопотока в профиле. Доступные форматы передаются в заголовке `quality` при получении ссылки на трек:
* `128K` — Экономичный режим.
* `256K` — Стандартное качество (по умолчанию).
* `320K` — Высокое качество.
* `ALAC` — Lossless (доступно только с Premium-подпиской).

система автоматически ограничивает выбор (`stream.max_quality`) на основе ответа `/health` и статуса подписки.

## 3. Редизайн Библиотеки под Вкладку «Playlists»

Мы полностью переработали архитектуру раздела «Библиотека» в `LibraryScreen.kt`, отказавшись от небезопасных локальных пустых плейлистов и перейдя на полноценный облачный формат.

### 3.1 Архитектурная структура вложенных видов (Sub-views)
Экран разделен на 4 изолированных Compose-состояния с плавной навигацией:
1. **`MAIN` (Главное меню)**:
   Отображает три интерактивные карточки-раздела в стеклянном стиле (Glassmorphism):
   - **Favorites**: Считывает количество лайкнутых треков локальной Room БД. Клик открывает детальный список с кнопками Shuffle и Play.
   - **Downloads**: Отображает количество сохраненных офлайн-треков. Доступ контролируется проверкой статуса подписки ICM.
   - **Imported**: Отображает общее число перенесенных облачных плейлистов из Яндекс.Музыки и Apple Music.
2. **`FAVORITES`**: Список избранных треков Room.
3. **`DOWNLOADS`**: Список скачанных треков для офлайн-прослушивания.
4. **`IMPORTED`**: Облачный хаб перенесенных плейлистов.

### 3.2 Строгое разделение плейлистов по источникам (Headings Separation)
В виде `IMPORTED` плейлисты запрашиваются асинхронно через `IcmRepository.getUserPlaylists()`. Чтобы избежать путаницы и каши, элементы строго фильтруются по полю `source` и отображаются под отдельными заголовками:
* **Yandex Music**: Плейлисты, у которых `source?.lowercase()?.contains("yandex") == true`.
* **Apple Music**: Плейлисты, у которых `source?.lowercase()?.contains("apple") == true`.

Каждая секция снабжена счетчиком плейлистов, обложкой первого трека, названием, количеством треков и возможностью удаления с серверов ICM через подтверждающий диалог (`DELETE /me/playlists/{id}`).

## 4. Система Импорта и Предпросмотра Плейлистов

Импорт плейлистов — это сложный асинхронный процесс, сочетающий парсинг ссылок, парсинг метаданных и многоэтапный матчинг треков в Apple Music каталог.

### 4.1 Предпросмотр без импорта (`POST /me/playlists/preview`)
Позволяет пользователю увидеть треклист перед началом реального сопоставления. Это безопасный синхронный запрос, не записывающий ничего в базу данных.
```http
POST /api/partner/me/playlists/preview
Authorization: Bearer <token>
Content-Type: application/json

{
  "source": "yandex",
  "url": "https://music.yandex.ru/users/some-user/playlists/1004"
}
```
**Ответ для Yandex** (возвращает сырые метаданные без `trackId`):
```json
{
  "source": "yandex",
  "name": "Today's Hits Yandex",
  "total": 2,
  "tracks": [
    {
      "title": "Believer",
      "artists": ["Imagine Dragons"],
      "album": "Evolve",
      "duration_ms": 204000
    }
  ]
}
```

### 4.2 Запуск импорта (`POST /me/playlists/import`)
* **Apple Music (Синхронно)**: Ссылка на Apple Music (`music.apple.com/.../playlist/...`) содержит готовые треки Apple каталога. Импорт отрабатывает мгновенно, возвращая код `200` и `playlist_id`.
* **Яндекс.Музыка (Асинхронно)**: Требует сопоставления (матчинга) каждого трека. Запрос мгновенно возвращает код `202 Accepted` и `job_id`.

```http
POST /api/partner/me/playlists/import
Authorization: Bearer <token>
Content-Type: application/json

{
  "source": "yandex",
  "url": "https://music.yandex.ru/users/some-user/playlists/1004",
  "name": "Custom Playlist Name"
}
```
**Ответ (202 Accepted)**:
```json
{
  "job_id": "yandex_import_job_777",
  "status": "pending",
  "poll_url": "https://byicloud.online/api/partner/me/playlists/import/yandex_import_job_777",
  "poll_after": 3
}
```

### 4.3 Поллинг статуса задачи сопоставления (`GET /me/playlists/import/{job_id}`)
Для асинхронных задач (Яндекс.Музыка) приложение запускает корутину опроса (`delay(1500)`), которая проверяет статус задачи.

Согласно спецификации API, сопоставление проходит через три строгих статуса:
1. **`pending` (Задача выполняется)**:
   Сервер возвращает текущий прогресс:
   ```json
   {
     "status": "pending",
     "progress": {
       "total": 100,
       "matched": 45,
       "failed": 2
     }
   }
   ```
   *UI-эффект*: Отображается круговой индикатор загрузки, прогресс-бар и текстовый статус (например, `"Tracks: 47 / 100 (Matched: 45, Failed: 2)"`).
2. **`ready` (Задача успешно завершена)**:
   Система нашла все доступные треки и сохранила их в облачный плейлист пользователя:
   ```json
   {
     "status": "ready",
     "playlist_id": 1042,
     "total": 100,
     "matched": 95,
     "failed": 5
   }
   ```
   *UI-эффект*: Прогресс-бар заполняется до конца, выводится зеленое сообщение `"Playlist successfully imported!"`, и активируется кнопка закрытия диалога.
3. **`failed` (Произошел сбой на сервере)**:
   Система возвращает описание сбоя:
   ```json
   {
     "status": "failed",
     "error": "source_api_error",
     "message": "Yandex returned 502 after retries"
   }
   ```
   *UI-эффект*: Поллинг останавливается, выводится точная причина сбоя из поля `message`, а цвет индикаторов меняется на красный.

## 5. Разбор Критического Исправления: Баг HTTP 202

В процессе интеграции была выявлена и устранена фундаментальная проблема с обработкой асинхронных HTTP-ответов `202 Accepted` в OkHttp-клиенте (`IcmApi.kt`).

### 5.1 Описание проблемы
В OkHttp метод `response.isSuccessful` проверяет, лежит ли HTTP-код в диапазоне `200..299`. Следовательно, для кода `202` значение `isSuccessful` всегда равно `true`.

Исходная структура проверки ответов в `IcmApi.kt`:
```kotlin
// БАГ: isSuccessful перехватывает 202 до того, как сработает ветка else/code == 202
when {
    response.isSuccessful -> {
        Result.success(parseResponse<T>(response.body))
    }
    response.code == 202 -> {
        val pending = parseResponse<IcmAsyncTrackPending>(response.body)
        Result.failure(IcmAsyncPendingException(pending))
    }
}
```

**К чему это приводило:**
1. **При запросе холодного трека** (`/track?async=1`): Сервер возвращает `202` с телом `IcmAsyncTrackPending`. Поскольку `isSuccessful` срабатывал первым, клиент пытался десериализовать этот ответ в модель `IcmTrackResponse`. Происходило исключение десериализации (JSON parsing exception), и запрос падал с ошибкой.
2. **Если просто поменять ветки местами**: Тогда при импорте Яндекс-плейлиста (который тоже возвращает `202`, но с телом `IcmPlaylistImportResponse`) клиент заходил бы в ветку `202`, пытался распарсить тело как `IcmAsyncTrackPending` и выбрасывал бы ошибку, блокируя импорт.

### 5.2 Архитектурное решение (Фикс)
Мы внедрили интеллектуальное разделение 202-ответов по сигнатуре эндпоинта. Проверка `202` срабатывает как ошибка асинхронного трека **только для музыкальных стриминговых эндпоинтов** (содержащих `/track`), а для эндпоинтов импорта плейлистов (`/me/playlists/import`) ответ пропускается дальше как успешный:

```kotlin
// ИСПРАВЛЕННЫЙ ВАРИАНТ в execute() и executeSync():
when {
    response.code == 202 && endpoint.contains("/track") -> {
        // Асинхронное кэширование трека на сервере — возвращаем специальное исключение
        val pending = parseResponse<IcmAsyncTrackPending>(response.body)
        Result.failure(IcmAsyncPendingException(pending))
    }
    response.isSuccessful -> {
        // Обычный успешный ответ (включая 200 OK и 202 Accepted для старта импорта плейлистов)
        Result.success(parseResponse<T>(response.body))
    }
    else -> {
        // Обработка стандартных HTTP ошибок
        ...
    }
}
```
Этот лаконичный фикс полностью решил проблему сосуществования двух разных API-сценариев для кода `202` без усложнения структуры сетевого слоя.

## 6. Детальный Экран Облачного Плейлиста (`PlaylistDetailScreen.kt`)

При клике на импортированный плейлист в интерфейсе открывается детальный экран плейлиста. Мы обновили его логику для безопасного маппинга удаленных сущностей.

### 6.1 Динамическая загрузка данных
Треки запрашиваются через `IcmRepository.getUserPlaylistTracks(idLong)`.
Поскольку API возвращает Nullable-поля для элементов трека, мы добавили безопасный маппинг в конструктор внутренней модели `Track` приложения:
```kotlin
tracks = response.tracks.map { tr ->
    val durationSec = tr.duration ?: 0L
    val dMs = if (durationSec < 1000L) durationSec * 1000L else durationSec
    val trackIdStr = tr.trackId.orEmpty()
    Track(
        id = trackIdStr,
        title = tr.title.orEmpty(),
        artist = tr.artist.orEmpty(),
        albumName = "",
        uri = Uri.parse("https://byicloud.online/track/$trackIdStr"),
        durationMs = dMs,
        albumId = tr.collectionId?.hashCode()?.toLong() ?: trackIdStr.hashCode().toLong(),
        coverUrl = tr.cover?.replace("1000x1000", "600x600")
    )
}
```

### 6.2 Особенности воспроизведения
* **Потоковый стриминг**: Ссылка `uri` формируется динамически и указывает на прокси-эндпоинт `/track/{trackId}`, который автоматически резолвит аудиопоток на серверах ICM.
* **Запуск плеера**: Весь список треков передается в контроллер плеера с помощью `PlayerController.playFromList(tracks, startIndex)`.
* **Управление элементами**: Кнопка удаления конкретной песни из списка скрыта, поскольку ICM API спроектирован под неизменяемые облачные слепки плейлистов и поддерживает только полное каскадное удаление всего плейлиста (`DELETE /me/playlists/{id}`).
