ICM Music — Partner API

API для встраивания поиска и проигрывания музыки в сторонние приложения.

База: https://byicloud.online

Авторизация

API-ключ выдаём при подключении, формат pk_<id>_<random>. Передавать в заголовке:

X-Partner-Key: pk_yourname_xxxxxxxxxxxx

Если ключ утерян — напиши, выпустим новый.

Для запросов от лица конкретного юзера добавь X-Partner-User-Id: <id> — нужно для аналитики и per-user настроек (hide_explicit).

Какую модель выбрать #

Сценарий Кто стучится к нам Как авторизоваться Нужен CORS?
Server-to-server Твой backend → наш API. Клиент ходит только к твоему backend X-Partner-Key Нет
Client-direct JS в браузере юзера → наш API напрямую partner_session_token (выпускает твой backend) Да
Мобильный/нативный клиент Приложение → наш API partner_session_token или X-Partner-Key Нет

Session-токен (для клиентов в браузере / мобилке) #

API-ключ нельзя светить во фронте — любой пользователь увидит его в DevTools. Поэтому для прямых запросов с клиента ваш бэкенд выпускает короткоживущий токен и отдаёт его клиенту. Сам API-ключ остаётся только у вас на сервере

Выпуск на твоём бэкенде:

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"partner_user_id":"u_42","hide_explicit":false}' \
  https://byicloud.online/api/partner/session/issue

Параметры:

Поле Что это
partner_user_id Любой стабильный id юзера в твоей системе (1–128 символов). Сюда привязывается аналитика и per-user настройки
hide_explicit true если этот юзер должен видеть отфильтрованный поиск/треки. По умолчанию false

Ответ:

{
  "partner_session_token": "eyJhbGciOiJIUzI1NiJ9.eyJpc3MiOiJpY20tcGFydG5lciIsInBpZCI6Im1zZ3IiLCJ1aWQiOiJ1XzQyIiwic2NwIjpbInNlYXJjaCIsInN0cmVhbSJdLCJpYXQiOjE3NDcyMDAwMDAsImV4cCI6MTc0NzIwMzYwMH0.signature",
  "expires_in": 3600,
  "partner_user_id": "u_42",
  "scopes": ["search", "stream", "album", "artist", "meta"]
}
Поле Описание
partner_session_token JWT, по умолчанию 1 час жизни. TTL настраивается админом
expires_in Сколько секунд токен ещё валиден
scopes Список разрешённых эндпоинтов на момент выпуска. Если потом в админке изменим скоупы — это коснётся только новых токенов

Клиент использует токен так же как API-ключ, только в заголовке Authorization:

fetch("https://byicloud.online/api/partner/search?q=test", {
  headers: { "Authorization": `Bearer ${sessionToken}` }
})

CORS — когда и зачем #

CORS актуален только если фронт ходит к нам из браузера напрямую (схема client-direct). Если у тебя сервер посередине (server-to-server) — пропусти этот раздел, тебя это не касается.

Что такое CORS в двух предложениях. Браузер перед каждым cross-origin запросом смотрит, разрешил ли сервер этот origin. Если сервер не отдаёт заголовок Access-Control-Allow-Origin: https://chat.example.com — Chrome/Safari/Firefox блокирует ответ, и ты в DevTools видишь красную ошибку «blocked by CORS policy».

Как разрешить твой домен. Скажи нам где будет фронт — например https://chat.example.com. Мы добавим в whitelist. После этого браузер пропустит запросы.

Что важно:

  • Указывай полный origin со схемой: https://chat.example.com, а не chat.example.com и не https://chat.example.com/
  • Поддомены нужно добавлять отдельно: https://app.example.com и https://chat.example.com — это два разных origin'а
  • http://localhost:3000 для дев-разработки тоже можно добавить, не проблема

Как проверить что CORS настроен правильно. Открой консоль браузера, попробуй сделать fetch к нашему API с твоего домена. Если ошибки нет — настроено. Если есть «CORS error» — пиши, проверим.

Без CORS работает:
- curl из терминала
- Серверный код (Python/Node/Go) на твоём backend
- Postman / Insomnia
- Нативные мобильные приложения (iOS/Android SDK)

CORS нужен только когда:
- JS в браузере делает fetch() / XMLHttpRequest к нам
- WebView в мобильном приложении грузит твою веб-страницу и она ходит к нам

Когда обновлять токен:

  • Истёк (expires_in прошёл) → новый запрос за токеном из твоего бэкенда
  • Сменился юзер (логин/логаут) → выпуски токены per юзер, для другого partner_user_id нужен свой

Простая логика на клиенте:

let token = null;
let tokenExpiresAt = 0;

async function getToken() {
  if (token && Date.now() < tokenExpiresAt - 60_000) return token;
  const r = await fetch("/your-backend/icm-session", { credentials: "include" });
  const data = await r.json();
  token = data.partner_session_token;
  tokenExpiresAt = Date.now() + data.expires_in * 1000;
  return token;
}

Чего не делать:

  • Не клади токен в localStorage — это XSS-вектор. Держи в памяти (let token) или в HttpOnly cookie на твоём же домене
  • Не дёргай /session/issue на каждый запрос клиента — это съест твой session_issue rate-limit. Один токен живёт час, переиспользуй
  • Не пытайся вытащить API-ключ из токена — его там нет. Токен подписан отдельным секретом, ключ остаётся только у тебя на сервере

Полный флоу:

1. Юзер логинится у тебя           → ваша обычная авторизация
2. Клиент: GET /your-backend/icm   → твой эндпоинт
3. Твой бэкенд: POST /session/issue с X-Partner-Key + partner_user_id
4. Возвращает клиенту partner_session_token
5. Клиент ходит к /api/partner/* с Authorization: Bearer <token>
6. Через час — повторяет с шага 2

Параметры запроса:

Поле Что это
q Строка поиска. До 200 символов. Минимум 2 буквенно-цифровых символа — пустые/мусорные запросы ("", ' ') отбрасываются с 400 query_too_short. Если шлёшь много мусора подряд (≥10/мин) — получишь 429 query_spam_detected
region us / ru / nz. Должен быть из regions_allowed твоего ключа. Если не разрешён — подменяется на первый из списка
source apple (по умолчанию) / vk / all. См. раздел VK Music. vk/all требует чтобы vk был в твоём stream.allowed_sources — иначе 403 source_not_allowed
limit Опционально. Сколько items вернуть. Клампится сверху до partner.config.search.max_results (по умолчанию 30, в /health точное значение). Если не передан — берётся max_results

Что внутри items — три типа сущностей вперемешку. Различай по флагам isArtist и isAlbum:

Тип Условие Что делать дальше
Артист isArtist: true Открой страницу артиста через GET /artist/{id}
Альбом isAlbum: true Открой треклист через GET /album/{id}
Трек оба false Проигрывай через POST /track с этим id как trackId

Поля результата:

Поле Кто использует
id Всегда. Для трека = trackId, для альбома = collectionId, для артиста = artistId
cover Всегда. URL-шаблон Apple Music, можно менять размер: 1000x1000 → 300x300
preview Только у треков. 30-секундное превью с Apple Music. Не требует подписи, можно играть напрямую
is_explicit Только у треков. true если 18+
collectionId У треков — id альбома, к которому относится. У альбомов — то же что id
album У треков — название альбома. У альбомов и артистов отсутствует
artistName Только у артистов (там же где title)
isCustom true для наших собственных релизов независимых артистов

Региональная подмена. Если в запросе передан регион не из regions_allowed, мы подменим его на первый разрешённый и вернём в поле region. Всегда смотри что фактически использовано — это поле в ответе.

End-to-end сценарий:

# 1) Юзер вбил «believer» — ищем
curl -H "X-Partner-Key: pk_..." \
  "https://byicloud.online/api/partner/search?q=believer&region=us"
# Берём первый объект где !isArtist && !isAlbum → это трек, его id = 1440831203

# 2) Получаем плейбэк-URL
curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"trackId":"1440831203","region":"us"}' \
  https://byicloud.online/api/partner/track
# Берём поле url и отдаём в плеер

Подсказка по UX. Используй debounce 300мс на вводе пользователя — не дёргай API на каждую букву. Локальный кеш на (q, region) ещё сэкономит запросов.

Резолвит trackId в подписанный URL для проигрывания.

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"trackId":"1440831203","region":"us","quality":"256K"}' \
  https://byicloud.online/api/partner/track

  "track_id": "1440831203",

  "source": "apple",
  "quality": "256K",
  "artist_id": "358714030",

Параметры запроса:

Поле Что это
trackId id трека из /search или tracks[].id из /album
region us / ru / nz (зависит от того, что разрешено ключу). По умолчанию us
quality 128K, 256K, 320K, ALAC. Пожелание — режется до stream.max_quality из /health

Что в ответе:

Поле Описание
source apple / vk / custom / special — откуда взяли трек
quality Реально отданное качество (после кэпа)
url Абсолютная ссылка для стрима, действует до expires_at
expires_at Unix timestamp когда ссылка протухнет (обычно now + 600)
file_id Внутренний id файла. Полезно кэшировать — потом по тому же trackId мы вернём этот же file_id мгновенно

Возможные ошибки:

// Трек только в другом регионе
{ "error": "region_unavailable", "required_region": "ru" }   // 451

Повтори запрос с указанным required_region.

// TIDAL-трек / source отключён в конфиге
{ "error": "source_not_allowed", "source": "tidal" }         // 403

// Трек не найден ни в одном регионе
{ "error": "track_not_found" }                                // 404

Стрим аудио #

URL из поля url ответа /track подставляй прямо в плеер. Никаких заголовков авторизации не нужно — подпись уже в query-параметре.

<audio src="https://byicloud.online/api/partner/audio/BAAdf...?ps=...&pid=yourname" controls></audio>

Range / seek. Эндпоинт отдаёт Accept-Ranges: bytes, поэтому seek работает автоматически — <audio> сам делает Range-запросы при перемотке. Для своего плеера на fetch() можно явно:

curl -H "Range: bytes=500000-1000000" -o slice.m4a \
  "https://byicloud.online/api/partner/audio/BAAdf...?ps=...&pid=yourname"

Вернётся 206 Partial Content с заголовком Content-Range.

Скачать целиком:

curl -o track.m4a "https://byicloud.online/api/partner/audio/BAAdf...?ps=...&pid=yourname"

Когда URL истёк (10 минут). Если плеер ловит 403 invalid_or_expired_signature, просто позови /track заново с тем же trackId — получишь свежий URL. У нас сработает свой кеш, ответ придёт за миллисекунды.

const audio = document.querySelector('audio');
audio.addEventListener('error', async () => {
  const r = await fetch('/api/partner/track', {
    method: 'POST',
    headers: { 'X-Partner-Key': KEY, 'Content-Type': 'application/json' },
    body: JSON.stringify({ trackId, region: 'us' })
  });
  const { url } = await r.json();
  audio.src = url;
  audio.play();
});

Форматы. В ответе приходит audio/mp4 (m4a из Apple) или audio/mpeg (mp3 из VK) — все современные браузеры играют оба. Если в твоей платформе нужно строго одно — фильтруй по source (apple → m4a, vk → mp3).

Плейлисты Apple Music #

Тот же эндпоинт /album/{id} принимает редакционные плейлисты Apple Music. Их id начинается с pl., например pl.f4d106fed2bd41149aaacabb233eb5eb (Today's Hits) или pl.acc464c750b94302b8806e6fcde56e17 (Pop Hits).

curl -H "X-Partner-Key: pk_..." \
  "https://byicloud.online/api/partner/album/pl.f4d106fed2bd41149aaacabb233eb5eb?region=us"

Структура ответа та же, но с отличиями:

{
  "album": {
    "id": "pl.f4d106fed2bd41149aaacabb233eb5eb",
    "title": "Today's Hits",
    "artist": "Apple Music Pop",
    "cover": "https://.../1000x1000bb.jpg",
    "type": "playlist",
    "description": "The biggest songs of the moment...",
    "motionCoverUrl": "https://.../animated.mp4"
  },
  "tracks": [
    {
      "id": "1799855643",
      "title": "Some Song",
      "artist": "Some Artist",
      "collectionId": "pl.f4d...",
      "cover": "https://.../1000x1000bb.jpg"
    }

Отличия от обычного альбома:

  • type: "playlist" — отличай от "Album" / "Single"
  • artist — имя куратора (Apple Music, Apple Music Pop, и т.п.), а не музыканта
  • description — текстовое описание плейлиста (может быть пустой строкой)
  • motionCoverUrl — анимированная обложка mp4, если есть (необязательное поле). Можно вставить в <video autoplay muted loop> вместо статичной картинки
  • У каждого трека своя cover (в обычном альбоме всё с одной обложки)

Где брать pl. id:

  • Из ответа /api/partner/artist/{id} — в секции «куратор» / «featured»
  • Скопировать из ссылки Apple Music: music.apple.com/us/playlist/todays-hits/pl.f4d106fed2bd41149aaacabb233eb5eb → id после последнего /
  • Пользовательские плейлисты юзеров Apple Music через этот API недоступны — только редакционные/каталожные

Треки внутри плейлиста проигрываются точно так же — через POST /track с trackId оттуда.

VK Music

Партнёрский API поддерживает поиск и стрим из VK (через Moosic API) — полезно для треков, которых нет в Apple Music каталоге.

Включение #

Параметр vk должен быть в stream.allowed_sources твоего ключа (управляется админом в боте — попроси менеджера). Если выключен — любые vk_* запросы вернут 403 source_not_allowed.

Ограничения #

  • Lyrics и batch /tracks/meta для VK сейчас не поддерживаются — только Apple.
  • VK не имеет региональной привязки — параметр region для VK игнорируется.
  • Квалити: без линковки/подписки — MP3 256K, с активной подпиской ICM — MP3 320K. ALAC для VK недоступен (отдаём 320K вместо).
  • Первый запрос холодного VK-трека идёт 3–10 секунд (мы готовим файл нужного качества и кладём в кеш). Используй ?async=1 чтобы не блокировать клиент (см. раздел «Async-режим для /track»). Повторные запросы того же трека отдают file_id мгновенно.

Тексты треков (lyrics)

LRC-текст для трека. Сейчас поддерживаются:
- Apple Music — если файла нет на диске, скачиваем (1–10 сек).
- TIDAL — кешированный файл либо запрос к TIDAL API.
- Custom-треки — текстов нет, всегда 404 lyrics_not_found.

Scope: lyrics. Если выключен — 403 scope_not_allowed.

curl -H "X-Partner-Key: pk_..." \
  "https://byicloud.online/api/partner/track/1440831203/lyrics?region=us"

{
  "track_id": "1440831203",
  "source": "apple",
  "format": "lrc",
  "lyrics": "[00:00.00] First we found...\n[00:08.34] ..."
}

Параметры:

Поле Что это
track_id Apple id (123...), tidal_track_<n> или custom_<n>
region Опционально. По умолчанию первый из regions_allowed ключа

Ошибки:

Код Когда
403 scope_not_allowed Scope lyrics выключен в админке
404 lyrics_not_found Текст не найден ни на диске, ни в Apple/TIDAL API

Альтернатива по query. Есть зеркальный эндпоинт GET /api/partner/lyrics?track_id=...&region=... — он эквивалентен track/{id}/lyrics. Используй любой.

Что важно. На холодных Apple-треках первый запрос может занять до 10 секунд. Последующие — мгновенно из кеша. Не дёргай lyrics пачкой на 100 треков сразу — лучше lazy load при открытии плеера.

Личный кабинет (для линкованных юзеров)

Эндпоинты под /me/* работают только если запрос пришёл от линкованного юзера с активной подпиской ICM (через X-Partner-User-Id или partner_session_token).

Иначе:
- 401 partner_user_required — partner_user_id не передан
- 403 user_not_linked — юзер ещё не привязан (см. «Линковка аккаунтов»)
- 403 subscription_required — линковка есть, но подписка истекла или нет
- 403 scope_not_allowed — scope user_quality_choice выключен

Scope для всех /me/* — user_quality_choice.

Выбор качества стрима #

Линкованный юзер с подпиской может выбрать качество выше лимита партнёра. Например, у партнёра max_quality: 256K, но юзер с ICM-подпиской хочет 320K — это делается через preferences.

Получить текущий выбор:

curl -H "X-Partner-Key: pk_..." -H "X-Partner-User-Id: u_42" \
  https://byicloud.online/api/partner/me/preferences

{
  "partner_user_id": "u_42",
  "quality_preference": "320K",
  "max_quality": "320K",
  "allowed_qualities": ["128K", "256K", "320K", "ALAC"],
  "updated_at": 1747200000
}

Сохранить выбор:

curl -X PUT -H "X-Partner-Key: pk_..." -H "X-Partner-User-Id: u_42" \
  -H "Content-Type: application/json" \
  -d '{"quality":"320K"}' \
  https://byicloud.online/api/partner/me/preferences

Передай {"quality": null} чтобы сбросить выбор (вернётся auto = max доступное по подписке).

Что важно:

  • quality_preference применяется автоматически в /track если у юзера активна подписка. Параметр quality в /track имеет приоритет — это override на конкретный запрос.
  • Если у юзера нет линковки/подписки/scope — сохранённый preference игнорируется и работает старая логика (cap_quality до тарифа партнёра).
  • В /health для линкованного юзера со scope появится linked_user.user_quality_choice: true и linked_user.current_preference: "320K".

Когда юзер послушал трек из волны (дослушал / пропустил / переключил в середине) — отправь это событие. Сигналы попадают в playback_history, и ранжирование волны автоматически их подхватит: avg_completion бустит знакомые треки, skip_count штрафует.

Параметры:

Поле Что это

played_seconds Сколько секунд реально слушал (не позиция плеера, а накопленная игра). Обязательный.
total_seconds Длительность трека. Опциональный — но без него мы не сможем посчитать completed/skipped, и тогда волна не учтёт сигнал в полной мере.
completed Опциональный bool. Если не указан — считаем по played >= 0.85 * total.
skipped Опциональный bool. Если не указан — считаем по played < 0.15 * total.

Поле logged в ответе: true если событие записалось. false для не-Apple track_id (VK/TIDAL/custom) — волна их не ранжирует, поэтому сигнал тихо игнорируется. На клиенте можно слать одинаково для всех треков, нам это не вредит.

Scope: library_wave_playback. Когда слать — рекомендуем после audio.ended или при переключении трека (вычитай played_seconds из audio.currentTime минус скипы вперёд).

404 album_not_found VK альбом не найден в Moosic
404 artist_not_found VK артист не найден в Moosic
404 track_not_found Трек не найден ни в одном регионе (Apple) или в Moosic (VK)
404 lyrics_not_found Текста нет ни на диске, ни в Apple/TIDAL API
401 partner_user_required Эндпоинт /me/* или /library/* требует partner_user_id
403 user_not_linked Юзер не привязан к ICM-аккаунту
403 subscription_required Нет активной ICM-подписки для /me/*
429 rate_limited Превышен лимит запросов
451 region_unavailable Трек недоступен в этом регионе, в ответе есть required_region
401 invalid_api_key_format Ключ не в формате pk_<partner_id>_<32-символьный-секрет>
401 token_revoked Session-токен был отозван (например, ротация ключей)
403 s2s_only Эндпоинт требует API-ключ (/session/issue, /link/email/*) — нельзя вызывать с session-токеном
404 job_not_found_or_expired /track/job/{id} — job старше 10 минут или не существует
403 job_belongs_to_another_partner Полез за чужим job_id
404 user_not_found /me/profile — линковка есть, но юзер в users отсутствует (теоретически невозможно, защита)

При 429 в ответе и заголовке Retry-After — сколько секунд ждать.

Лимиты

Лимиты — запросы в минуту на ключ. Считаются раздельно по группам:

  • search — /search
  • stream — /track
  • session_issue — /session/issue
  • default — /album, /artist, /track/{id}/meta, /cover-sign, /lyrics, /track/{id}/lyrics, /me/preferences, /me/profile, /library/likes, /library/subscriptions, /library/wave/* (включая /library/wave/playback)

Сам стрим (/audio, /cover) лимитом не считается.

Точные значения — в ответе /health.

Что и как кешировать у себя #

У нас уже стоит свой кеш (search ~10 минут, метаданные треков ~7 дней), так что повторные запросы к нам быстрые. Но кеш на твоей стороне экономит твой rate-limit и убирает сетевой round-trip:

/search — кешируй ответы на 60 секунд по ключу (query + region). Чаще всего пользователи дотыпывают одну букву — каждый раз бить в API не нужно.

// псевдо
const KEY = `search:${region}:${q.toLowerCase()}`;
const cached = cache.get(KEY);
if (cached) return cached;
const data = await fetch(...);
cache.set(KEY, data, 60);

Метаданные треков и альбомов (/track/{id}/meta, /album/{id}) — кешируй на сутки и больше. Альбом редко меняется. Инвалидируй вручную если пользователь жалуется на устаревшую обложку.

file_id из ответа /track — кешируй на сутки и больше по ключу (trackId + region + quality). Сам трек в нашем хранилище не меняется. Имея сохранённый file_id, можно потом перевыдавать только signed URL — но проще снова дёргать /track: у нас сработает наш кеш и ответ придёт за миллисекунды.

partner_session_token — кешируй пока не истёк (expires_in секунд). Не дёргай /session/issue на каждый запрос клиента.

Что НЕ кешировать #

  • Поле url из ответа /track и /cover-sign — это короткоживущая подпись (10 минут). Когда истечёт — снова позови /track или /cover-sign, получишь свежий URL.
  • Сам аудио-файл (/audio/{file_id}) — это твой собственный стрим из кеша Telegram через нас, его никуда сохранять не надо. Браузер сам закеширует через Cache-Control: public, max-age=604800 (неделя).

Простой расчёт #

С нормальным кешем у тебя на 100k активных юзеров в день получится примерно:
- /search: 1-2 rpm от твоего бэкенда (всё гасится локальным кешем)
- /track: всплески при старте плеера, ~10-20 rpm
- /album, /artist, /meta: единицы rpm

То есть дефолтных лимитов хватит на старт даже большого приложения. Если упрёшься — напиши, поднимем.

Batch-запросы

Если нужно загрузить метаданные нескольких треков (например, плейлиста) — не дёргай /track/{id}/meta в цикле, а отправь один batch:

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"track_ids":["1440831200","1440831201","1440831203"]}' \
  https://byicloud.online/api/partner/tracks/meta

{
  "count": 3,
  "items": [
    { "id": "1440831200", "title": "...", "artist": "...", "cover": "...", "duration": 199853 },
    { "track_id": "1440831201", "error": "not_found" },
    { "id": "1440831203", "title": "Believer", ... }
  ]
}

До 50 треков за запрос. Запрос съедает один meta rate-limit-hit вместо 50.

Async-режим для `/track`

Если трек ещё не закеширован у нас — /track может ждать 1–5 секунд (а ALAC и до минуты), пока мы скачаем и подготовим файл. Чтобы не блокировать клиент — добавь ?async=1:

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"trackId":"1440831203"}' \
  "https://byicloud.online/api/partner/track?async=1"

Если трек тёплый — приходит обычный 200 с url.
Если холодный — приходит 202 Accepted:

{
  "job_id": "a3f5b1c20d8e4f72",
  "status": "pending",
  "poll_url": "https://byicloud.online/api/partner/track/job/a3f5b1c20d8e4f72",
  "poll_after": 2
}

Опрашивай poll_url раз в 2 секунды:

curl -H "X-Partner-Key: pk_..." \
  https://byicloud.online/api/partner/track/job/a3f5b1c20d8e4f72

Пока status: pending — продолжай. Когда status: ready — внутри ответа есть url, expires_at и всё остальное как у обычного /track. Job хранится 10 минут.

Линковка аккаунтов (привязка к ICM)

Если хочешь, чтобы юзер с подпиской ICM Music автоматически получал её преимущества (высокое качество, расширенные источники) — нужно связать его partner_user_id с его аккаунтом ICM. Есть два способа: через Telegram (HTML-редирект) и через email (чистый JSON API).

Способ 1. Через Telegram (HTML-редирект) #

Кратко: ты редиректишь юзера на нашу страницу с кнопкой Telegram Login, он нажимает её, мы получаем подтверждение от Telegram и редиректим обратно к тебе с icm_user_id.

Схема URL

Твой UI ───► https://byicloud.online/partner/<partner_id>/link?partner_user_id=u_42&redirect_uri=https://chat.example.com/callback&state=<random>
                                          │
                                          ▼ (наш сервер рендерит страницу с виджетом)
                       https://telegram.org/js/telegram-widget.js
                                          │
                                          ▼ (юзер нажал Login, Telegram редиректит)
                       https://byicloud.online/partner/link/complete?nonce=...&id=...&hash=...
                                          │
                                          ▼ (наш сервер линкует и редиректит)
Твой UI ◄───  https://chat.example.com/callback?state=<random>&linked=1&icm_user_id=1406840236

Важно: /partner/link/complete — это наш внутренний URL, его задаёт сервер автоматически (в data-auth-url виджета). Ты этим URL не пользуешься, твоя задача — только редиректнуть юзера на /partner/<partner_id>/link и принять финальный редирект на свой redirect_uri.

Параметры запроса (/partner/<partner_id>/link)

Поле Что это
partner_user_id id юзера в твоей системе (1–128 символов). Именно сюда привяжется ICM-аккаунт
redirect_uri Куда мы редиректим после линковки. Должен быть в whitelist твоих origins (config.session.allow_origins)
state Любая твоя случайная строка. Вернём её в редиректе. Проверяй для защиты от CSRF

Что возвращается в redirect_uri

Успех:

https://chat.example.com/callback?state=<твой>&linked=1&icm_user_id=1406840236

Ошибка авторизации Telegram:

https://chat.example.com/callback?state=<твой>&linked=0&error=telegram_auth_failed

Ошибка БД при линковке:

https://chat.example.com/callback?state=<твой>&linked=0&error=link_failed

Что важно

  • redirect_uri сверяется по схеме+хосту (https://chat.example.com) с whitelist'ом в твоём конфиге. Trailing-slash и path значения не имеют. Если хоста нет в whitelist → 400 redirect_uri_not_allowed (страница не откроется).
  • state — твоя случайная строка, проверь её при возврате (защита от CSRF).
  • icm_user_id — это Telegram-id юзера (он же users.user_id в нашей БД). Можешь сохранить у себя для связи в дальнейшем.
  • Линковка идемпотентна — повторный проход того же юзера просто обновит маппинг.

Если ты разрабатываешь мобильное приложение

Telegram Login Widget — это веб-виджет. Он требует cookies, redirect и JS — то есть полноценный браузер. Внутри обычного WebView (особенно WKWebView на iOS) виджет работает нестабильно.

Правильно:

  1. Открывай страницу /partner/<id>/link?... в системном браузере:
    - Android: Chrome Custom Tabs (androidx.browser.customtabs.CustomTabsIntent)
    - iOS: SFSafariViewController или ASWebAuthenticationSession
  2. В redirect_uri используй custom-scheme deep link твоего приложения, например myapp://oauth/icm. Мы делаем стандартный 302 на любой URL из whitelist — браузер передаст deep link обратно в твоё приложение.
  3. Чтобы мы приняли myapp:// в redirect_uri, попроси нашего менеджера (t.me/trmrcd) добавить myapp:// в твой whitelist.

Не работает: обычный WebView с redirect_uri=https://.... Telegram перенаправит, но твой WebView не сможет перехватить редирект и закрыть себя.

Распространённые ошибки

Открывается главная страница вместо виджета
- Проверь URL: должно быть /partner/<id>/link (с /link в конце и partner без s).
- Хост в redirect_uri не в whitelist — попроси менеджера добавить.

404 Not Found на /api/partner/auth/telegram
- Такого эндпоинта нет. Используй /partner/<partner_id>/link (HTML) или /api/partner/link/email/request (JSON).

401 invalid_api_key_format на /session/issue
- Формат ключа — pk_<partner_id>_<32-символьный-секрет>, а не просто pk_<partner_id>. Полный ключ выдан один раз при создании партнёра. Если потерял — попроси менеджера ротировать (старый ключ сразу инвалидируется).

400 redirect_uri_not_allowed
- Хост в redirect_uri не в whitelist (config.session.allow_origins). Точное совпадение по scheme://host[:port]. Передай менеджеру нужный origin.

400 Link session expired or invalid на /partner/link/complete
- Юзер прошёл по ссылке старше 10 минут или дёрнул callback напрямую. Начни флоу заново.

Способ 2. Через email (JSON API, с авто-регистрацией) #

Если ты не хочешь редиректить юзера на нашу страницу — используй OTP-флоу. Партнёр сам рисует UI (поле для email и поле для 6-значного кода), а наш API только верифицирует.

Регистрация on-demand. Если введённого email ещё нет в нашей системе — мы автоматически создадим ICM-аккаунт при первом /request. Юзеру не нужно отдельно регистрироваться у нас заранее. После успешного /verify его email будет считаться подтверждённым, и мы отправим юзеру отдельным письмом сгенерированный временный пароль, которым он может зайти в ICM напрямую (на byicloud.online). Этот пароль рекомендуем сразу сменить — либо через эндпоинт /password/change (см. ниже), либо в настройках ICM.

Шаг 1 — попросить код:

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"partner_user_id":"u_42","email":"user@example.com","state":"optional"}' \
  https://byicloud.online/api/partner/link/email/request

{
  "sent": true,
  "nonce": "Bx7y...urlsafe24",
  "expires_in": 600
}

На указанный email уходит письмо с 6-значным кодом. Ответ одинаковый и для новых, и для существующих аккаунтов — партнёру не нужно различать кейсы. На один email — не чаще одного запроса в минуту (429 rate_limited).

Шаг 2 — ввести код:

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"nonce":"Bx7y...","otp":"123456"}' \
  https://byicloud.online/api/partner/link/email/verify

{
  "linked": true,
  "icm_user_id": 1406840236,
  "state": "optional",
  "password_issued": true
}

Поле password_issued — true, когда юзер был только что зарегистрирован/верифицирован и на его email отправлено письмо со сгенерированным временным паролем. Покажи ему сообщение вроде «мы отправили вам пароль на почту — проверьте». Для уже верифицированных юзеров (повторный линк, например, после смены partner_user_id) — false, пароль не трогаем.

Возможные ошибки:

Код Ответ Когда
400 {"error":"invalid_nonce"} nonce истёк (>10 минут) или не существует
400 {"error":"invalid_otp","attempts_left":N} код неправильный; можно повторить, всего 5 попыток на nonce
400 {"error":"nonce_locked"} израсходованы все 5 попыток — nonce и OTP удалены, нужно запрашивать заново
403 {"error":"nonce_belongs_to_another_partner"} nonce был выдан другому партнёру
429 {"error":"rate_limited","retry_after":N} request на тот же email чаще раза в минуту

Что важно:

  • Оба эндпоинта работают только по X-Partner-Key (S2S). Не пытайся вызывать их с partner_session_token — вернёт 403 s2s_only.
  • nonce одноразовый: после успешного verify сразу удаляется. Если линковка нужна повторно (например, юзер сменил email-аккаунт) — запрашивай новый nonce.
  • state опциональный — если передал, мы вернём его в ответе verify, удобно для корреляции с твоим UI.
  • OTP живёт 10 минут.

Способ 2.1. Смена пароля линкованного юзера #

После авто-регистрации юзер получает сгенерированный пароль на email. Чтобы он мог сменить его прямо из твоего UI — есть отдельный эндпоинт:

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"partner_user_id":"u_42","current_password":"oldPass123","new_password":"myNewPass456"}' \
  https://byicloud.online/api/partner/link/email/password/change

{ "changed": true }

Что важно:

  • Только S2S (X-Partner-Key). 403 s2s_only иначе.
  • Юзер должен быть уже залинкован к твоему partner_id. Если линка нет или он принадлежит другому партнёру — 404 user_not_linked.
  • current_password обязателен — это доказательство, что юзер реально владеет аккаунтом. Партнёр выступает транспортом: запроси оба пароля у юзера в форме, передай нам, мы сравним server-side. Сами пароли не логируем.
  • new_password — минимум 8 символов. Должен отличаться от текущего, иначе 400 new_password_must_differ.
  • При неправильном current_password — 401 invalid_current_password.
  • Если юзер забыл пароль — используй /password/reset (см. ниже). Мы сгенерируем новый пароль и пришлём на email юзера.

Способ 2.2. Сброс пароля линкованного юзера (forgot password) #

curl -X POST -H "X-Partner-Key: pk_..." -H "Content-Type: application/json" \
  -d '{"partner_user_id":"u_42"}' \
  https://byicloud.online/api/partner/link/email/password/reset

{ "reset": true }

Мы генерируем новый пароль, обновляем хеш в БД и шлём пароль письмом на email юзера. Старый пароль сразу инвалидируется — то есть если юзер где-то залогинен через /api/auth/email/login, его сессия по-прежнему работает (мы их не отзываем), но новые попытки войти со старым паролем будут падать. Партнёру сам пароль НЕ возвращается.

Что важно:

  • Только S2S. Партнёр может ресетить только своих линкованных юзеров (404 user_not_linked иначе).
  • Per-email cooldown 60 сек — иначе 429 rate_limited с retry_after.
  • Если у юзера нет email-аккаунта в ICM (например, был линкован через Telegram-флоу, у него только Telegram-id) — 404 email_account_missing. Для таких юзеров reset через партнёра не работает.
  • Если SMTP временно недоступен — пароль в БД всё равно меняется. Юзеру придётся повторить reset, когда почта починится.

Что это даёт #

После линковки в нашей БД появляется связь partner_user_id ↔ users.user_id, и для запросов с этим partner_user_id (через X-Partner-User-Id или partner_session_token) мы на лету апгрейдим конфиг, если у юзера активная ICM-подписка:

Поле Без подписки (или без линковки) Линкованный + подписка
stream.max_quality по тарифу партнёра (обычно 256K) 320K
stream.allowed_sources по тарифу партнёра (обычно [apple, vk]) [apple, vk, special, custom]
stream.block_special_releases true (по умолчанию) false

Эффект применяется к /search, /track и /health. Чтобы партнёр мог отдебажить — в /health для линкованного подписчика появится дополнительное поле:

{
  "...": "обычные поля /health",
  "linked_user": {
    "icm_user_id": 1406840236,
    "subscription_upgrade": true,
    "effective_stream": {
      "max_quality": "320K",
      "allowed_sources": ["apple", "custom", "special", "vk"]
    }
  }
}

Если линковки нет или подписка истекла — секция linked_user отсутствует.

Подписка проверяется на каждый запрос, но кешируется на 60 секунд — после оплаты или истечения подписки эффект применяется в течение минуты.

X-Request-Id

Каждый ответ от нашего API содержит заголовок:

X-Request-Id: a3f5b1c20d8e4f72

Если что-то пошло не так — пришли этот id, мы найдём конкретный запрос в логах. Можешь передавать свой X-Request-Id в запросе — мы используем его (полезно когда у тебя сквозной trace через несколько сервисов).

Версионирование API

В каждом ответе от /api/partner/* есть заголовок:

X-API-Version: 1

В разделе /health это поле тоже есть: "api_version": "1".

Гарантируем что в рамках v1:
- URL и формы запросов не меняются
- Существующие поля в ответах остаются (могут добавляться новые)
- Коды ошибок остаются стабильными

Если будем менять что-то ломающее — выкатим v2 под другим префиксом, оставив v1 рабочим минимум 6 месяцев.
